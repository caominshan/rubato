# Hey Tablo 用户反馈分析方案

## 目标

把“用户点击了反馈按钮”升级成可分析的产品闭环：记录用户是否看到推荐、是否选择切片、是否打开来源，以及负反馈后的新结果是否促成继续播放。

## 事件模型

```ts
type ProductEvent =
  | "query_submitted"
  | "recommendation_shown"
  | "segment_selected"
  | "source_opened"
  | "feedback_clicked"
  | "recommendation_replanned"
  | "memory_saved"
  | "translation_corrected";
```

当前首页已接入前六种事件；`memory_saved` 和 `translation_corrected` 为后续粉丝记忆与中韩翻译模块预留。

事件只记录行为、匿名会话 ID、轮次、segmentId 和反馈类型，不保存用户输入原文、模型回答全文或密钥。

## 四个核心指标

| 指标 | 当前计算口径 | 要回答的问题 |
|---|---|---|
| 推荐点击率 | 发生切片选择的推荐轮次 / 推荐曝光轮次 | 推荐有没有吸引用户继续了解 |
| 来源打开率 | 打开原视频的切片 / 被选择的切片 | 用户是否愿意消费完整内容 |
| 负反馈率 | 发生负反馈的推荐轮次 / 推荐曝光轮次 | 推荐是否匹配当前需求 |
| 反馈后播放率 | 重规划后打开来源的轮次 / 成功重规划轮次 | 反馈是否真的改善结果 |

看板还提供从“提交需求”到“打开来源”的会话漏斗，以及四类负反馈的分布。

## 数据策略

当前个人项目采用浏览器 `localStorage`：

- 不需要数据库即可完成3–5人主持式测试。
- 每个浏览器最多保留最近500条事件。
- 看板可切换“演示数据”和“本机体验”。
- 演示数据始终显示 `DEMO DATA · 非真实运营数据`。
- 本机数据可以一键清空。

它适合原型验证，但不属于生产埋点。正式上线后应将事件发送到服务端事件管道，并增加登录用户去重、设备归因、统一统计周期、隐私授权和异常流量过滤。

## 防止指标失真

- 点击率按“会话 + 轮次”去重，重复点击同一推荐不会反复增加。
- 没有分母时返回0，不展示 `NaN`。
- 演示数据和真实数据完全分开。
- 指标页面公开展示计算口径。
- 不把本地测试结果描述为线上活跃度。

## 自动化验证

新增4个指标测试，验证演示数据计算、重复点击去重、空数据稳定性、反馈分布和漏斗。当前项目总计16个自动化测试。
