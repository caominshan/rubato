# Hey Tablo：用户反馈分析与 Insights 看板

> 适用场景：腾讯音乐 Bubble 产品策划实习面试、AI 产品项目答辩、产品数据复盘  
> 本轮目标：把四个反馈按钮升级成可以记录、计算和分析的产品反馈闭环

## 1. 这一轮做了什么

在上一阶段，Hey Tablo 已经允许用户对推荐给出四种反馈：

```text
太说教
不够好笑
太沉重
换个方向
```

Agent 会根据反馈更新约束、排除历史结果并再次检索。但当时只有交互闭环，没有分析闭环：系统知道用户点了按钮，却没有回答以下问题：

- 推荐有没有吸引用户继续查看？
- 用户有没有打开完整原视频？
- 哪种负反馈最常出现？
- Agent 重新规划后，结果是否真的变好了？

因此我增加了一个轻量的产品分析系统，包括：

1. 统一的用户行为事件 Schema。
2. 首页六个真实交互埋点。
3. 浏览器本地事件存储。
4. 明确标注的 Demo Data。
5. `/insights` 用户反馈分析页面。
6. 四个核心产品指标。
7. 用户交互漏斗。
8. 四类负反馈分布。
9. 最近事件流。
10. 四个指标自动化测试。

完成后，项目自动化测试从12个增加到16个：

```text
Test Files：3 passed
Tests：16 passed
TypeScript：passed
Next.js production build：passed
```

## 2. 为什么需要做用户反馈分析

只有反馈按钮，不等于真正分析了用户反馈。

原来的链路是：

```text
用户点击“太说教”
→ Agent 更换约束
→ 返回新推荐
```

升级后的链路是：

```text
用户看到推荐
→ 是否选择某个声音切片
→ 是否打开完整来源
→ 是否给出负反馈
→ Agent 是否成功重新规划
→ 重新规划后是否继续选择和打开来源
→ 汇总成产品指标
→ 找出下一版本的问题
```

它对应岗位描述中的两项核心工作：

> 收集并分析用户反馈。  
> 提出优化方案，提升用户体验与活跃度。

这里的产品判断是：

> 反馈是否有效，不能只看按钮点击成功，而要继续观察用户在新结果上是否产生了更深行为。

例如，用户点击“太说教”并不代表功能成功。只有当新结果返回后，用户继续选择片段甚至打开原视频，才能初步说明重新规划改善了体验。

## 3. 事件埋点是什么

事件埋点可以理解为：当用户完成一个对产品有意义的动作时，系统记录一条结构化事件。

例如用户点击一个推荐，不是只在浏览器里切换卡片，还会记录：

```json
{
  "name": "segment_selected",
  "conversationId": "conversation_xxx",
  "turn": 1,
  "segmentId": "hd-ep19-xx",
  "episode": 19,
  "occurredAt": "2026-09-26T10:00:00.000Z",
  "source": "live"
}
```

这样后续才能回答：

- 一共出现过多少轮推荐？
- 有多少轮发生了选择？
- 哪个片段被打开？
- 负反馈发生在第几轮？
- 用户反馈后有没有继续操作？

事件不是页面截图，也不是服务器日志。它是专门为产品分析设计的业务记录。

## 4. 事件 Schema 是怎么设计的

统一 Schema 位于：

```text
lib/analytics/schema.ts
```

事件名称包括：

```ts
type ProductEventName =
  | "query_submitted"
  | "recommendation_shown"
  | "segment_selected"
  | "source_opened"
  | "feedback_clicked"
  | "recommendation_replanned"
  | "memory_saved"
  | "translation_corrected";
```

### 当前已经接入的六个事件

| 事件 | 什么时候记录 | 产品意义 |
|---|---|---|
| `query_submitted` | 用户提交收听需求 | 用户开始一次任务 |
| `recommendation_shown` | 成功展示一轮推荐 | 用户获得了推荐曝光 |
| `segment_selected` | 用户切换声音节点 | 某条推荐产生兴趣 |
| `source_opened` | 用户打开原视频 | 用户希望继续消费完整内容 |
| `feedback_clicked` | 用户点击四种负反馈 | 当前推荐没有完全匹配 |
| `recommendation_replanned` | 新一轮推荐成功返回 | Agent 完成重新规划 |

### 预留的两个事件

```text
memory_saved
translation_corrected
```

它们分别为未来的“粉丝记忆收藏”和“中韩翻译修正”功能预留。当前界面还没有这两项功能，因此不会产生这两类真实事件。

### 每条事件可以包含的字段

```ts
{
  id: string;
  name: ProductEventName;
  occurredAt: string;
  conversationId?: string;
  turn?: number;
  segmentId?: string;
  episode?: number;
  feedback?: AgentFeedback;
  recommendationCount?: number;
  source: "live" | "demo";
}
```

### 为什么使用固定枚举

如果直接记录中文按钮文案，将来把“太沉重”改成“想轻松一点”，历史数据就会出现两个不同名称。

使用稳定枚举：

```text
too_preachy
not_funny_enough
too_heavy
not_relevant
```

界面文案可以变化，分析口径不会改变。

## 5. 为什么为每次请求生成 conversationId

指标不能只统计事件总数，还需要知道哪些事件属于同一次用户任务。

当用户第一次提交需求时，前端生成：

```ts
const conversationId = crypto.randomUUID();
```

然后同时用于：

- `query_submitted` 事件。
- `/api/agent` 请求。
- Agent session。
- 后续反馈和重新规划。
- Insights 指标去重。

因此一次完整会话可以被串起来：

```text
conversation A / turn 1 / query
conversation A / turn 1 / recommendation shown
conversation A / turn 1 / segment selected
conversation A / turn 1 / feedback clicked
conversation A / turn 2 / recommendation replanned
conversation A / turn 2 / source opened
```

`conversationId` 表示同一个任务，`turn` 表示第几轮推荐。

这让系统既能分析一次会话，也能分析反馈前后的变化。

## 6. 首页埋点接在哪里

### 6.1 提交需求

在 `PromptComposer` 中，用户点击提交后记录：

```ts
trackProductEvent("query_submitted", {
  conversationId,
  turn: 1,
});
```

这里只记录行为，不保存输入框原文。

### 6.2 推荐曝光

API 成功返回后记录：

```ts
trackProductEvent("recommendation_shown", {
  conversationId: response.session.conversationId,
  turn: response.session.turn,
  recommendationCount: response.result.recommendations.length,
});
```

只有成功展示结果才算曝光，提交失败不会计算为推荐曝光。

### 6.3 选择声音切片

用户点击声纹上的节点时记录：

```ts
trackProductEvent("segment_selected", {
  conversationId,
  turn,
  segmentId,
  episode,
});
```

### 6.4 打开来源

用户点击“播放这一段”时记录：

```ts
trackProductEvent("source_opened", {
  conversationId,
  turn,
  segmentId,
  episode,
});
```

这不是记录视频是否播放完成，只能证明用户主动打开了来源。

### 6.5 点击负反馈

点击反馈后、发送新请求前记录：

```ts
trackProductEvent("feedback_clicked", {
  conversationId,
  turn,
  feedback,
});
```

### 6.6 重新规划成功

只有新推荐成功返回时才记录：

```ts
trackProductEvent("recommendation_replanned", {
  conversationId,
  turn: nextTurn,
  feedback,
});
```

如果请求失败，只存在 `feedback_clicked`，不存在 `recommendation_replanned`。这样可以区分用户表达了不满意和系统是否成功处理。

## 7. 为什么使用 localStorage

正式产品一般会把事件发送到服务端埋点系统，但这是一个个人 MVP，目前没有用户账户、数据库和线上数据平台。

因此使用浏览器 `localStorage`：

```text
用户完成行为
→ 写入结构化事件
→ 保存在当前浏览器
→ Insights 页面读取
→ 计算指标
```

### 优点

- 不需要额外数据库。
- 不需要用户登录。
- 没有网络也能记录。
- 适合3–5人的主持式可用性测试。
- 可以直接演示完整反馈分析流程。

### 限制

- 只能看到当前设备和浏览器的数据。
- 用户清除缓存后数据消失。
- 无法跨设备去重。
- 不适合正式运营统计。
- 不能替代腾讯内部的数据平台。

### 存储保护

- 最多保留最近500条事件。
- 每条事件先经过 Zod 校验。
- 解析失败时返回空数据，不让页面崩溃。
- 用户可以一键清空本机事件。

面试时可以这样说：

> MVP 阶段我用 localStorage 验证事件模型和指标口径，而不是先搭建超出项目规模的数据基础设施。正式上线时会把同一套 Schema 接入服务端事件管道。

## 8. 隐私上记录什么、不记录什么

当前记录：

- 匿名 conversationId。
- 推荐轮次。
- segmentId。
- episode 编号。
- 反馈枚举。
- 事件时间。

当前不记录：

- 用户输入的原始文本。
- 模型完整回答。
- 用户姓名、手机号或设备信息。
- API Key。
- 浏览器 Cookie。

这是刻意的最小化原则：

> 为了计算产品指标，只收集必需的行为数据，不因为“以后可能有用”就收集用户内容。

## 9. 四个核心指标如何计算

指标计算位于：

```text
lib/analytics/metrics.ts
```

它是独立的纯函数，不依赖 React 页面，也不直接读取 localStorage。

这样做的好处：

- 指标可以单独测试。
- 将来换数据库不需要重写公式。
- 页面只负责展示，不负责临时拼数字。
- 产品口径更容易审查。

### 9.1 推荐点击率

```text
发生切片选择的推荐轮次
÷
推荐曝光轮次
```

演示数据：

```text
12 ÷ 16 = 75.0%
```

它回答：

> 用户看到推荐后，是否至少有一条让他想进一步查看？

这里按“conversationId + turn”去重。用户在同一轮重复点击同一节点，不会把点击率刷高。

### 9.2 来源打开率

```text
打开原视频的切片数
÷
被选择的切片数
```

演示数据：

```text
8 ÷ 12 = 66.7%
```

它回答：

> 用户产生兴趣以后，是否愿意离开摘要，继续消费完整内容？

这是 Hey Tablo 对内容平台更有价值的指标，因为 Agent 的目标不是代替原节目，而是把用户带回真实内容。

### 9.3 负反馈率

```text
发生负反馈的推荐轮次
÷
推荐曝光轮次
```

演示数据：

```text
4 ÷ 16 = 25.0%
```

它回答：

> 当前推荐有多少轮没有满足用户？

负反馈率不是越低越好。如果入口太隐蔽，用户不点击反馈，数字也会很低。因此要结合点击率、退出率和访谈原话一起判断。

### 9.4 反馈后播放率

```text
重新规划后打开来源的轮次
÷
成功重新规划的轮次
```

演示数据：

```text
3 ÷ 4 = 75.0%
```

它回答：

> 用户说“不满意”后，新一轮推荐有没有重新赢回他的兴趣？

这是最能证明反馈闭环价值的指标。

## 10. 为什么不能直接统计点击总数

假设同一个用户连续点击三个声音节点：

```text
推荐曝光：1次
节点点击：3次
```

如果直接计算：

```text
3 ÷ 1 = 300%
```

这个点击率没有意义。

因此推荐点击率采用“推荐轮次是否发生过点击”的口径：

```text
conversationId + turn
```

作为唯一键进行去重。

来源打开率则使用：

```text
conversationId + turn + segmentId
```

去重，因为它分析的是具体被选择的内容。

这说明产品指标不仅是做除法，更重要的是先定义统计对象和去重规则。

## 11. 交互漏斗是什么

Insights 页面提供四层漏斗：

```text
提交需求
→ 看到推荐
→ 选择切片
→ 打开来源
```

演示数据为：

```text
提交需求：12
看到推荐：12
选择切片：9
打开来源：5
```

每一层都按 conversationId 去重。

漏斗可以帮助判断问题出现在哪一层：

### 提交需求很多，看到推荐很少

可能是：

- API 失败。
- 模型超时。
- 用户输入经常不合法。
- 信息不足处理过于严格。

### 看到推荐很多，选择切片很少

可能是：

- 推荐标题没有吸引力。
- 推荐理由太技术化。
- 三条内容差异不明显。
- 声纹节点不容易理解或点击。

### 选择切片很多，打开来源很少

可能是：

- 摘要已经满足需求。
- 播放按钮不明显。
- 用户不愿跳转 YouTube。
- 推荐内容有吸引力，但完整节目太长。

因此漏斗不是为了画漂亮图，而是为了定位体验问题。

## 12. 负反馈分布怎么用

Insights 页面统计：

```text
太说教
不够好笑
太沉重
换个方向
```

如果真实测试中“太说教”明显最多，可以提出：

- 降低建议型内容权重。
- 增加陪伴、共鸣类片段。
- 调整 Answer Agent 的推荐理由语气。
- 在初始输入中增加“不需要建议”快捷选项。

如果“不够好笑”最多，可以检查：

- humour 标签质量。
- 笑点是否依赖上下文。
- 英文幽默翻译是否丢失语气。
- 排序公式是否过度偏向语义相关，而忽略娱乐性。

如果“换个方向”最多，可能说明系统理解了关键词，却没有理解用户真正的场景。

这才是从用户反馈到优化方案的完整逻辑：

```text
反馈数据
→ 找到主要问题
→ 提出原因假设
→ 修改产品或排序
→ 再看指标是否改善
```

## 13. Demo Data 为什么必须明确标注

个人项目刚开始没有真实用户，如果看板全部为空，无法展示分析结构；但如果放一组数字又不说明来源，会让人误以为是真实运营成绩。

因此我设计了两个数据模式：

### 演示数据

页面标记：

```text
DEMO DATA · 非真实运营数据
```

作用是：

- 演示四个指标如何计算。
- 展示漏斗和反馈分布。
- 让面试官理解未来真实数据接入后的页面。

### 本机体验

页面标记：

```text
LOCAL DATA · N EVENTS
```

它读取当前浏览器真实操作产生的事件。如果还没有事件，会显示空状态并引导用户返回 Agent 页面完成一次推荐。

演示数据和本机事件通过 `source` 字段严格区分：

```ts
source: "demo" | "live"
```

二者不会混合计算。

## 14. 演示数据是怎样构造的

演示数据模拟12次匿名会话：

- 12次提交需求。
- 12次第一轮推荐曝光。
- 9次发生切片选择。
- 5次打开原视频。
- 4次负反馈。
- 4次成功重新规划。
- 3次重新规划后打开来源。

四种负反馈各出现一次，便于完整展示分布。

演示数据使用固定时间和固定事件 ID，而不是每次随机生成。这样测试结果可以稳定复现。

## 15. Insights 页面展示了什么

访问路径：

```text
/insights
```

页面由五部分组成。

### 第一部分：数据来源

- 演示数据。
- 本机体验。
- Demo Data 警示。
- 清空本机数据。

### 第二部分：四张指标卡

- 推荐点击率。
- 来源打开率。
- 负反馈率。
- 反馈后播放率。

每张卡不只显示百分比，还显示：

- 分子。
- 分母。
- 指标定义。

### 第三部分：交互漏斗

展示从提交需求到打开来源的逐层变化。

### 第四部分：反馈分布

展示四类不满意原因分别出现多少次。

### 第五部分：最近事件流

展示事件类型、匿名会话、轮次和时间。

页面底部再次声明：

> 演示数据只用于展示分析方法，不代表真实用户表现。

## 18. 如何用真实体验数据做3人测试

即使没有线上用户，也可以使用“本机体验”模式做主持式测试。

### 测试前

1. 打开 `/insights`。
2. 切换“本机体验”。
3. 清空旧事件。
4. 回到 Agent 首页。

### 给用户三个任务

1. 找一段适合当前状态的节目。
2. 如果结果不满意，选择一个反馈。
3. 找到并打开最想听的原视频。

### 测试后

回到 `/insights` 查看：

- 是否成功提交需求。
- 是否切换推荐。
- 是否打开来源。
- 是否点击负反馈。
- 反馈后是否继续播放。

还需要记录用户原话，因为小样本定量数据不能解释全部原因。

例如：

```text
U01：“我不知道蓝色圆点可以点。”
U02：“推荐理由太像产品说明，不像朋友推荐。”
U03：“我想直接听这一分钟，不想跳完整视频。”
```

然后把行为数据和访谈原话结合起来提出改进。

## 19. 怎样根据指标提出优化方案

### 情况一：推荐点击率低

可能方案：

- 强化三条推荐的差异。
- 用中文场景标题代替原始英文节目标题。
- 提高声音节点的可点击感。
- 在推荐理由中先说用户能获得什么。

### 情况二：来源打开率低

可能方案：

- 显示片段预计时长。
- 将“播放这一段”放到更明显位置。
- 支持带时间戳直接跳转。
- 提供30秒试听，而不是直接离开产品。

### 情况三：负反馈率高

需要先看具体分布，不能只调整一个总指标。

- “太说教”高：降低建议类内容。
- “不够好笑”高：提高 humor 权重并改善幽默翻译。
- “太沉重”高：提高情绪强度过滤。
- “换个方向”高：加强场景理解和主题多样性。

### 情况四：反馈后播放率低

说明按钮虽然可以工作，但重新规划没有解决问题。需要检查：

- 反馈是否映射成了正确约束。
- 新一轮是否只做了表面换一批。
- 排序是否仍被原始关键词主导。
- 推荐理由是否解释了本轮为什么不同。

## 20. 两分钟面试讲述版本

> 前一版 Hey Tablo 已经支持“太说教、不够好笑、太沉重和换个方向”四种反馈，并能更新约束、排除旧结果、重新检索。但这还只是功能闭环，我无法判断用户反馈后体验有没有真的改善。所以这一轮我补了一套轻量的产品分析系统。
>
> 我先定义了统一的事件 Schema，目前首页真实记录需求提交、推荐曝光、声音切片选择、来源打开、负反馈和重新规划成功六类事件。每条事件使用 conversationId 和 turn 串起同一次会话以及反馈前后的不同轮次，但不记录用户输入原文、模型完整回答或密钥。
>
> 在指标层，我重点选择了推荐点击率、来源打开率、负反馈率和反馈后播放率。前三个分别观察推荐吸引力、完整内容消费意愿和匹配问题；反馈后播放率用来判断 Agent 重新规划后有没有重新赢回用户。所有指标都按会话和轮次去重，避免同一用户重复点击把点击率算到100%以上。
>
> 因为个人项目还没有线上用户，我提供了明确标记为 Demo Data 的固定样例，同时可以切换到当前浏览器的真实体验数据。演示数据和真实数据通过 source 字段隔离，不会混合。看板还展示从提交需求到打开来源的漏斗、四类负反馈分布和最近事件流。
>
> 最后我增加了四个自动化测试，验证指标计算、重复点击去重、空数据和反馈分布。目前项目共有16个测试。这个版本让我不仅能说“用户可以反馈”，还可以说明怎样判断反馈功能是否真正改善了用户体验。

## 22. 面试官可能追问的问题

### Q1：为什么选择这四个指标？

它们分别覆盖推荐曝光后的兴趣、完整内容消费、匹配失败和反馈修复效果，能连接从推荐到重新规划的完整路径。

### Q2：为什么不看日活和留存？

当前没有线上用户和连续多日数据，计算 DAU、次日留存没有意义。MVP 先验证单次任务是否成功，部署后再增加长期指标。

### Q3：这些数据是真实用户吗？

演示页默认是固定 Demo Data，并在页面显著标注；本机体验模式只记录当前浏览器的真实操作。两者不会混合。

### Q4：为什么不用数据库？

个人 MVP 先验证事件模型与指标口径，localStorage 成本低且足够支持小样本测试。生产环境会迁移到服务端事件管道。

### Q5：为什么不记录用户输入，之后不是无法分析需求吗？

当前先遵循数据最小化原则，避免收集敏感情绪文本。后续如果确实需要分析需求，应先做用户授权、脱敏、分类后存储，而不是直接保存原文。

### Q6：点击率为什么按轮次去重？

同一轮可以切换多个节点，直接用点击总数除以曝光会超过100%。按会话和轮次判断是否发生过选择，更符合“这一轮是否吸引用户”的问题。

### Q7：打开来源等于播放成功吗？

不等于。当前只能证明用户点击了来源链接，无法证明完成播放。正式接入播放器后应增加 `play_started`、`play_30s` 和 `play_completed`。

### Q8：负反馈率越低越好吗？

不一定。入口太隐蔽也会造成低反馈率，需要结合点击率、退出情况和访谈原话判断。

### Q9：反馈后播放率有什么缺陷？

样本量小时波动很大，而且无法完全证明播放由重新规划导致。正式实验需要更大样本、统一窗口和对照组。

### Q10：如果正式上线会怎样改？

将事件发送到服务端数据管道，增加用户授权、设备与账户去重、事件版本、失败重试、统一统计周期、异常流量过滤和可视化监控。

## 24. 不要说错的地方

- 不要说75%是真实用户推荐点击率，它来自 Demo Data。
- 不要说已经接入腾讯的数据平台，目前是 localStorage。
- 不要说打开来源等于播放完成。
- 不要说负反馈率25%代表产品质量差或好，脱离样本和对照无法判断。
- 不要说有线上用户增长数据，目前只有本机体验能力。
- 不要说记录了用户输入，目前刻意不保存输入原文。
- 不要说 `memory_saved` 和 `translation_corrected` 已经上线，它们只是预留事件。
- 不要说完成了因果实验，目前是描述性分析。
- 不要说所有点击都参与点击率，当前按会话与推荐轮次去重。
- 不要说指标测试证明了真实用户满意，它只证明计算逻辑正确。
