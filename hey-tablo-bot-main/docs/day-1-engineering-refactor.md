# Hey Tablo：第一阶段工程重构复盘

> 文档用途：项目复盘、简历素材、面试讲述准备  
> 阶段目标：把单文件 HTML 原型改造成可以继续接入 AI Agent 与 RAG 的 Next.js 工程

## 1. 一句话概括

我把一个约 1.4 MB、接近 9000 行的单文件 HTML 原型，重构成基于 Next.js、TypeScript 和 App Router 的前端工程，并完成数据抽离、组件化、首屏交互优化和环境变量配置，为后续接入 AI Agent、内容检索和流式回答建立工程底座。

## 2. 重构背景

原始版本把以下内容全部放在同一个 HTML 文件中：

- 页面结构
- CSS 样式
- JavaScript 交互
- 节目数据
- 字幕片段
- 图片资源
- 学习数据

它可以展示，但不适合继续开发，主要存在四个问题。

### 2.1 数据与页面强耦合

节目和字幕直接嵌在页面脚本中，无法方便地被检索模块、接口或 Agent 调用。

### 2.2 页面难以维护

所有功能都在一个文件里。修改一个区域可能影响其他区域，也不利于测试、复用和多人协作。

### 2.3 无法安全接入模型

纯前端 HTML 没有可靠的服务端边界。如果直接调用模型，API Key 很容易暴露在浏览器中。

### 2.4 缺少持续迭代能力

后续需要增加对话、检索、收藏、历史记录、埋点和用户系统，继续在单文件上叠加功能会使复杂度快速失控。

因此，这一阶段没有急于接入模型，而是先解决工程结构问题。

## 3. 技术选型

本阶段使用：

- Next.js 16
- React
- TypeScript
- App Router

选择 Next.js 的原因不是为了增加技术名词，而是由后续 Agent 能力倒推：

- 前端页面和服务端接口可以维护在同一仓库
- 模型密钥可以只保存在服务端
- 后续可增加 `/api/agent` 流式接口
- 可以逐步增加对话页、收藏页和用户页
- 适合部署到 Vercel
- TypeScript 可以约束节目、字幕和 Agent 返回结果

## 4. 本阶段完成的工作

### 4.1 初始化 Next.js 工程

建立了完整的项目配置：

- `package.json`
- `tsconfig.json`
- `next.config.ts`
- `next-env.d.ts`
- `.gitignore`
- `app/` App Router 目录

项目支持以下命令：

```bash
npm run dev
npm run build
npm run typecheck
npm run extract:data
```

这一步把项目从“能打开的页面”变成了“能安装、能开发、能检查、能构建、能部署的工程”。

### 4.2 保留旧版本作为迁移基线

原始页面没有被删除，而是移动到：

```text
legacy/index-v4.6.1.html
```

这样处理的目的：

- 防止迁移时丢失原有能力
- 随时进行视觉与数据对照
- 保留项目演进记录
- 必要时可以回溯旧实现

### 4.3 从旧 HTML 中抽取业务数据

新增数据迁移脚本：

```text
scripts/extract-legacy-data.mjs
```

脚本从旧 HTML 中识别并解析：

```js
const EPISODES = ...
window.HEY_TABLO_LEARNING_DATA = ...
```

然后输出为独立文件：

```text
data/episodes.json
data/transcript-segments.json
data/extraction-report.json
```

最终提取结果：

- 29 期节目
- 500 条字幕片段
- 390 条已验证片段

这不是单纯整理文件，而是在为 RAG 检索做准备：

```text
用户需求
→ 查询理解与改写
→ 字幕片段召回
→ 条件过滤与重排序
→ Agent 生成推荐理由
→ 返回节目、时间点和引用依据
```

节目元数据可以用于筛选和展示，字幕片段可以作为检索的最小单元，`sourceVerified` 字段可以参与可信度控制。

### 4.4 按职责拆分页面组件

首页拆分为：

```text
components/editorial/EditorialHeader.tsx
components/editorial/HeroArtwork.tsx
components/editorial/PromptComposer.tsx
app/page.tsx
```

各组件职责：

- `EditorialHeader`：品牌与主导航
- `HeroArtwork`：艺术化主视觉和装饰信息
- `PromptComposer`：快捷需求、最近会话、文本输入和提交反馈
- `page.tsx`：页面组合与数据统计读取

拆分原则不是简单按视觉区域切文件，而是按照功能职责划分。输入区域后续需要管理 Agent 请求状态，所以被拆成独立的客户端交互组件；首页主体继续保持适合服务端渲染的结构。

### 4.5 完成首页核心交互

首页没有直接使用通用聊天框，而是围绕“用户此刻想听什么”设计。

用户可以通过两种方式表达需求：

1. 选择快捷需求，例如：
   - 很累，只想有人陪
   - 通勤 20 分钟，想快速提神
2. 自由描述：
   - 当前状态
   - 可用时间
   - 想获得的感受
   - 不希望听到的内容

提交后页面展示 `REQUEST CAPTURED` 状态。目前没有伪造 AI 回答，真实 Agent API 将在后续阶段替换提交逻辑。

### 4.6 把核心操作控制在首屏内

第一版首页视觉完整，但输入框位于首屏以下，需要滚动才能看到。这会增加核心路径的操作成本：

```text
进入首页 → 理解产品 → 输入需求
```

如果输入框不在首屏，用户可能会把页面理解为展示网站，而不是一个可以立即使用的 Agent。

因此重新调整了：

- 顶部导航高度
- Hero 区域高度
- 标题字号和间距
- 主视觉尺寸与位置
- 快捷需求卡片高度
- 最近会话高度
- 输入框高度
- 页脚高度

最终在常见的 `1280 × 720` 桌面视口内，可以同时看到：

- 产品主标题
- 艺术化主视觉
- 两个快捷需求
- 最近一次会话
- 完整输入框与提交按钮
- 数据状态栏

压缩布局后还发现主视觉遮挡第二个快捷选项，因此进一步缩小插画并调整定位，解决了层级覆盖问题。

## 5. 环境变量与安全边界

新增 `.env.example`：

```env
OPENAI_API_KEY=
OPENAI_MODEL=
NEXT_PUBLIC_APP_NAME=Hey Tablo Agent
NEXT_PUBLIC_APP_STAGE=prototype
```

这里区分两类变量：

- `OPENAI_API_KEY`：仅服务端读取
- `NEXT_PUBLIC_*`：允许浏览器读取

模型密钥不能使用 `NEXT_PUBLIC_` 前缀，否则会进入前端构建产物并造成泄漏。`.env.local` 也被排除在 Git 提交之外。

## 6. 当前工程结构

```text

├── app/                         # Next.js 页面和全局样式

├── scripts/                     # 数据迁移脚本
├── .env.example                 # 环境变量示例
├── next.config.ts
├── package.json
└── tsconfig.json
```

目前已经形成三个清晰层次：

```text

数据层：节目数据与字幕片段
配置层：环境变量与工程配置
```

下一阶段将增加：

```text
Agent 层：意图理解、任务编排、回答生成
检索层：召回、过滤、重排序、引用
接口层：流式响应、错误处理、日志
```

## 9. 面试讲述版本

> Hey Tablo 最开始是一个接近 9000 行的单文件 HTML，视觉、交互和数据全部耦合在一起。它能用于展示，但不具备继续开发 AI 能力的工程基础。
>
> 所以第一阶段我没有急着接模型，而是先完成工程重构。我使用 Next.js、TypeScript 和 App Router 建立项目，把原始页面保留在 legacy 目录，避免迁移过程中丢失能力。然后我编写了数据提取脚本，从旧 HTML 中提取出 29 期节目和 500 条字幕片段，其中 390 条有来源验证，并分别保存成独立 JSON。
>
> 数据抽离的目的，是让节目元数据和字幕片段能够在下一阶段直接进入 RAG 检索，而不是继续被锁在页面代码里。前端部分则按照职责拆成导航、艺术主视觉和需求输入组件。
>
> 产品交互上，我没有直接做一个通用聊天框，而是让用户描述此刻的状态、可用时间和内容偏好，同时提供快捷需求降低输入成本。
>
> 在视觉验收时，我发现第一版输入框需要下拉才能看到，因此重新调整了首屏信息密度，把价值表达、快捷选项和输入框全部控制在一个桌面视口内。压缩后又发现插画遮挡交互区域，所以继续调整了视觉尺寸和层级。
>
> 最后，我通过 TypeScript 检查、Next.js 生产构建和真实浏览器交互完成验收。现在这个项目已经从静态页面变成了可以继续接入 Agent、检索和流式回答的产品工程。
