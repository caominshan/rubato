# Hey Tablo：检索与工具阶段复盘

> 文档用途：项目复盘、简历素材、面试讲述与技术追问准备  
> 阶段目标：不调用大模型，也能通过代码从 500 条字幕中检索出正确、可信、可解释的内容

## 1. 一句话概括

我为 Hey Tablo 实现了一套不依赖大模型的确定性检索内核：先用 Zod 统一字幕数据契约，再使用 MiniSearch 建立中英文全文索引，通过可解释的业务公式进行二次排序，最后把能力封装成四个可供 Agent 调用的工具，并用 6 个自动化测试验证召回、过滤、上下文和推荐结果。

## 2. 为什么没有直接接大模型

完成 Next.js 工程重构后，最容易想到的下一步是直接把用户问题发送给大模型。但这样做会带来三个问题。

### 2.1 模型并不知道节目内容

大模型的通用知识不能保证包含 Hey Tablo 每一期节目的准确字幕。即使模型听说过节目，也不能依靠它记住具体句子和时间点。

### 2.2 无法判断错误发生在哪一层

如果直接让模型输出推荐，一旦结果不准确，很难判断是：

- 没有找到正确内容
- 找到了，但排序错误
- 上下文不足
- 模型生成时发生幻觉

### 2.3 缺少可比较的效果基线

没有无模型检索基线，就无法证明后续增加 Agent 之后究竟提升了什么。

因此这一阶段先建立确定性链路：

```text
用户问题
→ 查询标准化
→ MiniSearch 召回
→ 业务排序
→ 条件过滤
→ 返回字幕、节目、时间点和来源
```

后续 Agent 负责理解任务和选择工具，而不是凭空回答节目内容。

## 3. 开始前的数据审计

现有数据包括：

- 29 期节目元数据
- 500 条字幕片段
- 390 条经过来源验证的字幕

字幕片段已有以下字段：

```ts
{
  id,
  episode,
  title,
  titleZh,
  startSeconds,
  endSeconds,
  timestamp,
  quote,
  meaningZh,
  noteZh,
  context,
  topics,
  emotions,
  desiredEffects,
  toneTags,
  sourceVerified,
  sourceUrl
}
```

数据已经比较丰富，但在进入检索之前仍需要解决两个问题：

1. JSON 文件本身不会约束字段类型，错误数据可能在运行时才暴露。
2. 用户使用中文表达，而大量主题和情绪标签使用英文。

## 4. 第一步：建立字幕 Schema

核心文件：

```text
lib/retrieval/schema.ts
```

我使用 Zod 定义了 `transcriptSegmentSchema`，让每条字幕都必须满足统一的数据契约。

### 4.1 基础类型约束

例如：

```ts
id: z.string().min(1)
episode: z.number().int().positive()
startSeconds: z.number().int().nonnegative()
sourceVerified: z.boolean()
sourceUrl: z.string().url()
```

这些规则保证：

- ID 不能为空
- 节目期数必须是正整数
- 时间不能为负数
- 来源验证状态必须明确
- 来源地址必须是合法 URL

### 4.2 跨字段校验

除了检查单个字段，还增加了：

```text
endSeconds >= startSeconds
```

如果片段结束时间早于开始时间，Schema 会直接报错。

### 4.3 为什么运行时校验和 TypeScript 都需要

TypeScript 只能检查代码中的类型，无法保证外部 JSON 的真实内容正确。Zod 会在程序运行时解析数据，因此二者分工不同：

- TypeScript：约束开发过程
- Zod：验证真实输入数据

测试结果显示，当前 500 条字幕全部通过统一 Schema。

## 5. 第二步：构建检索文档

核心文件：

```text
lib/retrieval/normalize.ts
```

原始字幕字段适合展示，但全文检索需要重新组织。我为每条字幕生成两个派生字段。

### 5.1 `searchText`

由以下字段合并而成：

```text
quote
meaningZh
noteZh
context
title
titleZh
```

它代表用户能够通过自然语言搜索的正文内容。

### 5.2 `tags`

由以下结构化标签合并而成：

```text
topics
emotions
desiredEffects
toneTags
```

它代表编辑和产品侧对内容的语义标注。

正文和标签被分开保留，是因为二者的意义不同：

- 正文回答“内容中具体说了什么”
- 标签回答“这段内容适合什么情境”

## 6. 第三步：处理中英文查询

MiniSearch 默认适合以空格和标点分隔的文本，但中文句子没有天然空格，因此我实现了自定义 tokenizer。

### 6.1 英文分词

英文文本会：

- 转小写
- 统一 Unicode 格式
- 去除多余空格
- 保留普通单词、数字、连字符和撇号结构

例如：

```text
Mentally Bulletproof
→ mentally, bulletproof
```

### 6.2 中文分词

中文文本会同时生成：

- 完整连续文本
- 单字 token
- 双字 token

例如：

```text
失恋难过
→ 失恋难过、失、恋、难、过、失恋、恋难、难过
```

这样可以在不引入大型中文分词服务的情况下，支持当前 500 条小型语料的基础中文检索。

### 6.3 为什么没有一开始就使用向量数据库

当前数据只有 500 条，MiniSearch 具备以下优势：

- 本地运行
- 无额外服务
- 查询延迟低
- 结果可重复
- 容易编写测试
- 方便解释字段权重

向量检索更适合语料继续扩大、用户表达更加开放的阶段。现在先建立关键词基线，可以降低系统复杂度，也能成为未来评估向量检索的对照组。

## 7. 第四步：中文意图扩展

仅做中文分词仍然不够，因为用户可能说“我失恋了”，而数据标签写的是 `heartbreak`。

因此增加了一个轻量、显式的查询映射表。

例如：

```text
失恋 → heartbreak、grief、comfort
心碎 → heartbreak、grief
孤独 → lonely、company、comfort
疲惫 → tired、low energy、comfort
职业 → career、starting over、impostor syndrome
变老 → aging、nostalgia、time perception
恐怖 → ghost、paranormal、chilling
追星 → fandom、fan、k-pop
```

用户原始输入不会被替换，而是与扩展词一起查询。

例如：

```text
原始输入：失恋后很难过，想被陪伴

扩展查询：
失恋后很难过，想被陪伴
heartbreak grief comfort sad permission to feel company lonely
```

这样可以同时保留用户原话和数据标签语义。

### 7.1 这种方案的优点

- 行为确定
- 容易测试
- 可以人工审核
- 不产生额外模型成本
- 适合作为无模型兜底

### 7.2 它的局限

- 需要人工维护词表
- 无法覆盖所有隐含表达
- 对复杂语义和否定句理解有限

因此它不是最终的意图理解方案，而是高可靠、低成本的第一层召回增强。

## 8. 第五步：建立 MiniSearch 索引

核心文件：

```text
lib/retrieval/index.ts
```

索引字段与权重为：

| 字段 | 权重 | 设计理由 |
|---|---:|---|
| `quote` | 4.0 | 原始字幕命中最有价值 |
| `meaningZh` | 3.2 | 中文用户经常按含义搜索 |
| `tags` | 2.8 | 支持情绪与使用场景匹配 |
| `context` | 2.5 | 补充单句缺少的上下文 |
| `noteZh` | 2.0 | 编辑说明具有辅助价值 |
| `titleZh` | 1.8 | 中文主题可帮助召回节目 |
| `title` | 1.4 | 英文标题相关，但不能压过字幕 |

这里最重要的判断是：字幕原句和中文含义应当比标题拥有更高权重。否则标题中的主题词可能让整期大量片段同时排到前面，降低具体字幕的准确性。

MiniSearch 同时开启：

- 多字段搜索
- 前缀匹配
- 英文轻度拼写容错
- OR 召回
- 条件过滤

拼写容错只对长度足够的英文词启用，避免短词模糊匹配产生大量噪声。

## 9. 第六步：设计二次排序公式

核心文件：

```text
lib/retrieval/ranker.ts
```

MiniSearch 可以完成文本召回和基础排序，但产品还需要考虑完整短语、业务标签和来源可信度，因此我增加了第二层排序。

最终公式：

```text
总分 =
6 × ln(1 + MiniSearch 相关度)
+ 2 × 完整短语命中
+ 0.8 × 标签重合数量
+ 0.75 × 来源已验证
```

### 9.1 文本相关度

```text
6 × ln(1 + MiniSearchScore)
```

使用对数是为了压缩 MiniSearch 原始分数差距，避免某个高频词或超高文本分完全支配最终排名。

### 9.2 完整短语命中

如果用户输入的完整短语直接出现在字幕、解释或上下文中，加 2 分。

例如搜索：

```text
mentally bulletproof
```

包含这句完整表达的片段会得到额外加分。

### 9.3 标签重合

用户查询与 `topics`、`emotions`、`desiredEffects`、`toneTags` 每重合一个有效标签，加 0.8 分。

这让情绪需求不仅依赖字面文本，也能使用人工策划数据。

### 9.4 来源可信度

`sourceVerified: true` 的片段加 0.75 分。

可信度不是绝对过滤，因为某些未验证片段仍可能有价值；只有用户或工具明确要求 `verifiedOnly` 时才会完全排除未验证内容。

### 9.5 为什么返回分数明细

每条搜索结果都会返回：

```ts
scoreBreakdown: {
  textRelevance,
  exactPhrase,
  tagOverlap,
  verifiedSource,
  total
}
```

这样可以回答：

- 为什么这条结果排第一？
- 它是正文命中还是标签命中？
- 来源验证对结果产生了多少影响？
- 调整哪一个权重可以改变排序？

这使排序从黑盒变成可调试、可解释的产品机制。

## 10. 第七步：实现检索过滤

搜索函数支持：

```ts
{
  episode?: number
  verifiedOnly?: boolean
  topics?: string[]
  emotions?: string[]
  desiredEffects?: string[]
  toneTags?: string[]
  limit?: number
}
```

过滤发生在候选结果进入业务排序之前，可以支持：

- 只查某一期节目
- 只返回来源已验证内容
- 只查某种情绪
- 只查某种预期效果
- 只查某种表达语气

例如：

```ts
searchSegments("ghost story", {
  verifiedOnly: true,
  limit: 10
})
```

会返回与鬼故事有关、且来源经过验证的字幕片段。

## 11. 第八步：封装四个 Agent 工具

核心文件：

```text
lib/tools/index.ts
```

工具不是四个独立的页面功能，而是未来 Agent 可以调用的确定性能力。

### 11.1 `search_transcript`

用途：搜索字幕并返回排序后的结果。

输入示例：

```ts
{
  query: "失恋后很难过，想被陪伴",
  limit: 5,
  verifiedOnly: true
}
```

输出包含：

- 字幕原句
- 中文解释
- 节目期数
- 时间点
- 来源链接
- 匹配词
- 排序分数明细

### 11.2 `get_episode`

用途：根据期数获取节目元数据，以及该期已有的字幕片段数量。

输入示例：

```ts
{
  episodeNumber: 4
}
```

Agent 可以先搜索片段，再用这个工具补充整期节目背景。

### 11.3 `get_segment_context`

用途：读取指定字幕及其前后片段。

输入示例：

```ts
{
  segmentId: "hd-ep01-02-hit-me-hard",
  neighborCount: 1
}
```

这个工具主要解决断章取义问题。Agent 在引用一句话前，可以先读取同一期、相邻时间的内容。

### 11.4 `recommend_segments`

用途：根据用户情境生成候选片段，并保证结果具有一定多样性。

输入示例：

```ts
{
  situation: "我最近对工作和未来很迷茫",
  desiredEffect: "想获得一点视角",
  limit: 3
}
```

它会：

1. 合并情境、预期效果和语气
2. 调用确定性检索
3. 默认只保留来源已验证内容
4. 对节目期数去重
5. 返回多个不同节目的候选片段

节目去重是一个产品判断：如果前三条结果全部来自同一期，虽然文本可能相关，但用户感受到的推荐多样性会很差。

## 12. 四个工具的关系

```text
用户表达需求
      ↓
recommend_segments
      ↓
search_transcript
      ↓
候选字幕片段
      ↓
get_segment_context ── 检查前后语境
      ↓
get_episode ───────── 补充节目背景
      ↓
Agent 组织最终回答
```

目前即使没有 Agent，也可以直接调用这些工具并获得结果。接入 Agent 后，模型只负责工具选择、参数组织和回答生成。

## 15. 完整面试讲述版本

> 完成 Next.js 工程重构之后，我没有立即把用户问题接到大模型，而是先建立了一套不依赖模型的检索基线。因为模型本身并不知道每一期节目的准确字幕，如果没有稳定的检索层，就无法区分错误来自召回、排序还是生成。
>
> 我首先用 Zod 整理了字幕 Schema，对 ID、节目期数、时间范围、来源链接和验证状态进行运行时校验。TypeScript 只能约束代码，而 Zod 能确保真正读取进来的 500 条 JSON 数据满足统一结构。
>
> 然后我使用 MiniSearch 对字幕原句、上下文、中文解释、节目标题和业务标签建立多字段索引。不同字段采用不同权重，字幕原句和中文含义权重最高，标题权重相对较低，避免整期主题压过具体内容。
>
> 因为用户使用中文表达，但很多内容标签是英文，我实现了自定义的中英文标准化和查询扩展。例如“失恋”会扩展为 heartbreak、grief 和 comfort。这样输入“失恋后很难过，想被陪伴”，不调用模型也可以召回正确主题的字幕。
>
> 在 MiniSearch 基础排序之后，我又增加了一层业务排序公式，综合文本相关度、完整短语命中、标签重合和来源可信度。每条结果都会返回分数明细，所以这个排序是可解释、可调试的，而不是黑盒。
>
> 最后我把检索能力封装成四个工具：字幕搜索、节目读取、字幕上下文读取和情境推荐。未来 Agent 只需要判断什么时候调用哪个工具，并组织最终回答，不需要凭空记忆节目内容。上下文工具可以减少断章取义，推荐工具则通过来源过滤和节目去重保证可信度与多样性。
>
> 我还写了六个自动化测试，覆盖真实数据 Schema、英文精确命中、中文情境召回、可信来源过滤、上下文读取和跨节目推荐。测试、TypeScript 检查和生产构建全部通过。这样后续即使接入大模型，也有一套稳定的无模型基线来衡量 Agent 是否真正带来了提升。

## 16. 30 秒精简版本

> 我为 Hey Tablo 建立了一套不依赖模型的字幕检索内核。首先用 Zod 统一 500 条字幕的 Schema，然后使用 MiniSearch 对原句、上下文、中文解释和情绪标签建立字段加权索引。为了支持中文输入，我增加了中文分词和可维护的中英文意图映射。召回后再根据文本相关度、完整短语、标签重合和来源可信度进行可解释排序。最后把这些能力封装成四个 Agent 工具，并用六个自动化测试验证正确性。这样模型只负责调用工具和生成回答，不负责凭空记忆内容。

## 17. 面试官可能追问的问题

### 为什么不用向量数据库？

当前只有 500 条字幕，MiniSearch 更轻、更快、更容易测试，也不需要额外服务。它先作为确定性基线。未来语料扩大、用户表达更开放时，可以升级为关键词与向量混合检索。

### 为什么需要二次排序？

全文搜索只考虑文本统计相关度，但产品还关心完整短语、情绪标签和来源可信度。二次排序把这些业务因素显式加入，并能返回分数明细。

### 为什么来源可信度只是加分，不直接过滤？

部分未验证片段仍然有召回价值，不应该在所有场景永久删除。默认排序给予可信来源优势；在正式引用或推荐场景中，通过 `verifiedOnly` 进行硬过滤。

### 中文词表是不是过于人工？

它确实不能覆盖所有表达，但优点是确定、可审核、无成本，非常适合早期验证和兜底。下一阶段可以由 Agent 生成结构化意图，再与规则扩展共同组成混合查询。

### 如何避免推荐全部来自同一期？

推荐工具会先扩大候选池，再按节目期数去重，最后截取用户要求的数量，以保证结果覆盖多个节目。

### 如何避免断章取义？

搜索结果返回片段 ID，Agent 在引用前可以调用 `get_segment_context`，读取同一期前后的字幕片段。

### 如何判断未来的 Agent 是否真的更好？

当前六个确定性测试构成最基础的回归集。后续还可以建立查询—期望片段数据集，对关键词检索、混合检索和 Agent 结果分别计算 Recall@K、MRR、来源准确率和人工满意度。
