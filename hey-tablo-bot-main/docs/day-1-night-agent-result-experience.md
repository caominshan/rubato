# Hey Tablo：真实 Agent 结果体验迭代复盘

> 适用场景：AI 产品经理面试项目讲解、作品集说明、技术追问准备  
> 本轮范围：真实 Agent 结果页、声音切片交互、逐集封面、信息密度、文案与一屏布局

## 1. 这一轮我解决了什么问题

这一轮没有继续增加 Agent 工具数量，而是集中解决“Agent 已经能返回真实结果，但用户看不懂、看不全，也感受不到播客产品特征”的问题。

最初的结果页只是把模型生成的一段回答和三条检索结果纵向排列。功能上能证明模型调用了工具，但体验上有四个明显问题：

1. 结果像搜索引擎列表，不像播客产品。
2. 模型回答、卡片和输入框纵向堆叠，页面需要滚动。
3. 推荐信息被压缩得太少，浪费了已经整理好的节目数据。
4. 用户再次提问时，旧结果会消失，页面重新回到首页，输入框发生跳动。

我的目标不是单纯“把页面变漂亮”，而是让结果页同时完成三件事：

- 让用户快速判断为什么推荐这一集。
- 让推荐结果有可验证的来源，而不是模型凭空生成。
- 用播客自己的视觉语言呈现 Agent 的检索过程。

最终我选择了“声音切片”作为结果页核心概念：三条推荐不是三张普通信息卡，而是声波上的三个可选择片段。

---

## 2. 核心产品思路：从“搜索结果”改成“声音切片”

### 2.1 为什么不用普通卡片列表

普通卡片列表虽然开发快，但无法表达 Hey Tablo 的内容媒介。它更像电商、资讯或搜索结果，用户只能看到三条互不相关的信息。

我把三条推荐放到同一条声波上，建立了更符合播客语义的关系：

- 一条声波代表 Agent 从节目库中找到的一组声音。
- 三个节点代表三个可以试听的时刻。
- 节点显示集数和时间戳，强化“结果来自真实节目片段”。
- 点击节点后，下方详情区同步切换，而不是跳转页面。

这种设计同时降低了页面复杂度：屏幕上只展开一个详情，另外两个结果保留为可见节点。

### 2.2 信息架构

结果页被拆成四层：

1. **Agent 回应**：一句自然语言回应用户此刻的需要。
2. **声音导航**：声波、三个节点、集数和时间戳。
3. **当前片段详情**：逐集封面、标题、内容简介、原文、中文解释、推荐理由、标签和评分。
4. **再次提问**：输入框始终位于下方，用户无需返回首页。

面试时可以概括为：

> 我没有把 Agent 输出直接当成一段文本渲染，而是先定义用户需要完成的判断任务，再把结构化输出映射成“回应—选择—判断—播放”的四层体验。

## 3. 我复用了哪些已有数据

这次没有为了视觉效果虚构内容。详情区的数据分别来自两类真实数据。

### 3.1 Agent 返回的片段级数据

来自结构化输出 `recommendations`：

- `segmentId`：片段唯一 ID。
- `episode`：集数。
- `timestamp`：片段时间戳。
- `title`：节目标题。
- `quote`：字幕原文。
- `meaningZh`：中文解释。
- `reason`：模型基于用户需求生成的推荐理由。
- `sourceUrl`：原始来源链接。
- `sourceVerified`：来源是否已验证。

### 3.2 本地节目库的集级数据

根据 `episode` 在 `data/episodes.json` 中查找对应节目，然后补充：

- `summaryZh`：本集内容概括。
- `editorNote`：人工编辑推荐说明。
- `toneTags`：情绪和语气标签。
- `scores.funny`：好笑程度。
- `scores.comfort`：安慰程度。
- `scores.reflection`：思考程度。
- `youtubeUrl`：每集对应视频地址。

这里的关键设计是：**模型只负责理解需求和解释匹配原因，事实内容、标题、时间戳、封面和评分全部来自本地可控数据。**

这避免了让模型重复生成已经存在的数据，也降低了幻觉风险。

## 4. 每集封面是怎么实现的

### 4.1 第一次实现为什么不对

第一版错误地使用了统一的 Hey Tablo 节目封面。它能说明节目品牌，却不能帮助用户区分三条推荐分别来自哪一期。

用户真正需要的是旧原型里的“每一集视频封面”。因此我重新检查了旧 HTML，确认旧版使用的是 YouTube 视频缩略图。

### 4.2 当前实现

前端从 `episode.youtubeUrl` 中提取视频 ID：

```ts
function getYoutubeThumbnail(youtubeUrl?: string) {
  if (!youtubeUrl) return "/hey-tablo-podcast-cover.jpg";
  const videoId = youtubeUrl.match(/(?:v=|youtu\.be\/)([\w-]{6,})/)?.[1];
  return videoId
    ? `https://i.ytimg.com/vi/${videoId}/hqdefault.jpg`
    : "/hey-tablo-podcast-cover.jpg";
}
```

每次用户切换声波节点时，`activeIndex` 改变，当前推荐、节目数据和封面同时更新。

### 4.3 兼容性问题

YouTube 的 `hqdefault.jpg` 通常使用 4:3 画布，但实际视频画面是 16:9，因此直接展示会出现上下黑边。

我的处理方式不是强行拉伸图片，而是：

```css
.slice-cover {
  aspect-ratio: 16 / 9;
  overflow: hidden;
}

.slice-cover img {
  width: 100%;
  height: 100%;
  object-fit: cover;
}
```

这样可以裁掉缩略图画布中的黑边，同时保持人物和食物画面不变形。

如果缩略图加载失败，`onError` 会回退到本地节目通用封面，避免出现破图。

## 5. 详情卡为什么展示这些信息

我没有简单恢复旧版的所有字段，而是围绕用户的三个判断问题重新组织：

### “这是什么？”

- 每集独立封面
- 集数和时间戳
- 完整节目标题
- 本集内容简介

### “为什么适合我？”

- Agent 生成的片段推荐理由
- 人工编辑说明
- 情绪标签
- 好笑、安慰、思考三项评分

### “它是真的吗？”

- 字幕原文
- 中文含义
- `SOURCE VERIFIED` 状态
- 跳转原始内容的播放入口

因此信息多，但每一项都有明确用途。它不是为了显得项目数据量大，而是减少用户点击播放前的不确定性。

## 6. 声波交互是怎么实现的

### 6.1 状态管理

`HeroResultStage` 使用本地状态保存当前选择：

```ts
const [activeIndex, setActiveIndex] = useState(0);
const activeItem = recommendations[activeIndex] ?? recommendations[0];
```

三个节点分别位于声波的 18%、50% 和 82% 处。点击节点执行：

```tsx
onClick={() => setActiveIndex(index)}
```

详情卡以 `segmentId` 作为 `key`，切换时重新触进入场动画：

```tsx
<article className="slice-detail" key={activeItem.segmentId}>
```

### 6.2 声波生成

为了避免额外引入音频可视化依赖，我先用确定性算法生成 64 根不同高度的声波柱：

```ts
const bars = Array.from(
  { length: 64 },
  (_, index) => 12 + ((index * 17 + index * index * 7) % 56),
);
```

它不是随机数，因此每次服务端和客户端渲染结果一致，也不会出现 hydration 不一致。

当前节点之前的声波显示蓝色，之后显示灰色，用来表达播放进度感。进入页面时通过 `scaleY` 动画让声波逐渐展开。

### 6.3 可用性优化

第一版声波上的 `01 / EP.19 / 20:49` 只有 7–9px，视觉上精致但不可读。我后来把字号提高到：

- 序号约 11px。
- 集数约 14px。
- 时间戳约 10px。

同时扩大节点的圆点与点击区域。这个修改体现了一个判断：**装饰性排版不能牺牲核心交互信息的可读性。**

## 7. 顶部 Agent 文案为什么重新设计

旧输出类似：

> 下饭推荐看韩国宵夜文化、粉丝跨界合作和独自吃饭的尴尬时刻。

这句话虽然正确，但有两个问题：

1. 它在机械总结三条结果，和下面的卡片重复。
2. 它像搜索引擎摘要，不像一个理解用户状态的 Agent。

因此我修改了 Answer Agent 的系统提示词：

- 回应用户处境，而不是罗列节目主题。
- 不超过 32 个中文字符。
- 禁止以“推荐看／推荐听”开头。
- 禁止重复三个推荐内容。
- 语气像一个有判断力的朋友。

目标输出类似：

> 今晚别一个人安静吃饭，让 Tablo 陪你热闹一会儿。

这里不是简单做文案润色，而是在划分信息职责：顶部负责情绪回应，卡片负责事实和解释。

## 8. 如何保持一屏和输入框稳定

### 8.1 遇到的问题

页面先后出现过三个布局问题：

- 卡片和输入框纵向堆叠，需要滚动。
- 卡片下方存在大块空白。
- 页面内容不足一屏时，footer 后面仍有空白区域。

最后一个问题的根因不是卡片高度，而是 `.page-shell` 只设置了 `min-height: 100svh`。内容不足视口时，footer 不会自动贴底。

### 8.2 最终布局

桌面端使用四行 CSS Grid：

```css
.page-shell {
  height: 100svh;
  min-height: 720px;
  display: grid;
  grid-template-rows: 52px minmax(320px, 1fr) auto 38px;
  overflow: hidden;
}
```

四行依次是：

1. 顶部导航。
2. 自动吸收剩余高度的主视觉或 Agent 结果。
3. 输入区域。
4. 数据状态栏。

这样输入框和状态栏始终在页面下方，剩余空间由主视觉区域吸收。

移动端取消固定视口网格并恢复正常滚动，因为小屏强制一屏会导致内容被裁切。这个处理体现了响应式设计不是简单等比例缩小，而是根据设备改变布局策略。

### 8.3 防止再次提问时输入框跳动

最初用户再次提交时会立即执行：

```ts
onResponseChange(null);
```

这会让结果页瞬间恢复首页，快捷问题和最近会话重新出现，输入框位置发生跳动。

我删除了这一步。现在提交新问题时保留旧结果，直到新结果成功返回再整体替换。这样还能避免网络请求期间出现空白状态。

这是一个典型的 perceived performance 优化：接口耗时没有改变，但页面稳定性和等待体验更好。

## 9. 视觉迭代中做过的取舍

### 取舍一：没有继续使用 AirDrop 弹窗

旧原型的 AirDrop 卡片很有记忆点，但放到桌面端结果页后会像一个悬浮模态框，遮挡背景信息，而且三条推荐只能机械翻页。

我保留了旧版“收到一段内容”的概念，但改成声波节点和展开详情，使交互更符合播客。

### 取舍二：不使用统一播客封面

统一封面适合品牌首页，但结果页更需要内容辨识。逐集封面能让用户快速理解推荐的题材差异，因此统一封面只作为加载失败的 fallback。

### 取舍三：保留高信息密度，但建立层级

我没有为了“极简”删掉已经整理好的数据，而是用封面、标题、内容、理由、评分和来源建立层级。产品上的简洁不是信息少，而是用户知道先看什么、后看什么。

### 取舍四：Trace 不作为主要内容

Agent Trace 对面试展示和调试很重要，但普通用户不需要一直阅读。因此它被放在页面底部并默认折叠，只显示模型、工具调用数和耗时。

## 12. 两分钟面试讲述版本

> 真实 Agent 接通之后，我发现技术链路虽然成立，但结果页仍然像一个搜索 Demo：模型回答很长，三条结果纵向罗列，需要滚动，而且没有利用我已经整理好的节目标签、评分和编辑说明。
>
> 所以我先重新定义结果页的任务。用户不是来看模型输出的，而是要判断“这是什么、为什么适合我、来源是否可信”。基于这个判断，我把结果页设计成“声音切片”：三条推荐放在同一条声波上，通过集数和时间戳形成三个节点，用户点击节点后只展开当前片段。
>
> 展开的详情不是让模型重新生成全部内容。我用 Agent 返回的 segmentId、quote、timestamp 和 reason 负责片段级信息，再用 episode number 关联本地 episodes.json，补充每集独立封面、内容简介、人工编辑说明、情绪标签以及好笑、安慰、思考评分。也就是说，模型负责理解与解释，事实信息来自确定性数据源。
>
> 实现过程中我还解决了几个真实问题。YouTube 的 hqdefault 是 4:3 画布，会出现黑边，所以我用 16:9 容器加 object-fit cover；声波节点最初字号太小，我扩大了文字和点击热区；顶部回答原来会机械罗列三个主题，我通过提示词把它改成一句回应用户状态的话；再次提交时保留旧结果直到新结果返回，避免输入框跳动；最后用 100svh 的四行 Grid 把导航、主视觉、输入区和状态栏固定在一屏内。
>
> 最终它不只是“模型能调用工具”，而是形成了一个可解释、可验证、符合播客媒介特征的 Agent 产品体验。

## 13. 面试官可能追问的问题

### Q1：为什么一定要做声波，普通卡片不是更简单吗？

普通卡片在效率上更简单，但缺乏媒介辨识度。声音切片不是纯装饰：它把三个结果压缩成一个选择器，让用户看到集数和时间戳，并且一次只聚焦一个详情，解决了信息密度和一屏展示的冲突。

### Q2：哪些内容由模型生成，哪些不是？

模型负责理解用户需要、从工具结果中选择片段，并生成简短推荐理由。节目标题、字幕原文、中文释义、时间戳、URL、验证状态、封面、标签和评分都来自检索证据或本地节目数据。这个边界能降低幻觉，并让结果可追溯。

### Q3：为什么不用模型直接生成评分？

评分属于产品的长期内容资产，需要跨请求稳定。如果每次由模型实时评分，同一集在不同请求中可能产生不同分数，也无法解释评分标准。因此评分由离线整理的数据提供，模型只使用它辅助表达。

### Q4：为什么保留 Trace？

Trace 一方面帮助开发定位模型是否真的调用工具、调用了哪个工具以及耗时；另一方面在作品集中能证明这不是预先写死的推荐。不过它不是普通用户的主任务，所以默认折叠。

### Q5：一屏设计会不会影响移动端？

会，所以我没有把桌面策略直接复制到移动端。桌面端使用固定视口 Grid；移动端恢复文档流和滚动，封面、字号、声波节点也使用独立断点调整。

### Q6：为什么新请求期间保留旧结果？

因为旧结果仍然是有效内容。如果立刻清空，用户会看到页面结构跳变，而且在十几秒模型等待期间没有内容可看。保留旧结果能提高界面稳定性和感知性能；新结果返回后再进行原子替换。

### Q7：如果 YouTube 封面加载失败怎么办？

图片使用 `onError` 回退到本地节目封面，因此外部缩略图不可用时不会出现破图。来源链接和字幕数据也不依赖封面请求。

### Q8：这轮最重要的产品判断是什么？

不是声波动画，而是数据职责分层：模型负责“理解和解释”，本地数据负责“事实和稳定属性”，前端负责“判断路径”。这让产品既有 Agent 能力，也不会把可信度完全交给模型。

## 14. 不要在面试中说错的地方

- 不要说声波来自真实音频波形。目前是前端确定性生成的视觉声波。
- 不要说封面存储在本地。逐集封面根据 YouTube URL 动态生成，只有 fallback 封面在本地。
- 不要说所有片段都已人工验证。界面会根据 `sourceVerified` 分别显示 VERIFIED 或 NEEDS REVIEW。
- 不要说模型生成了节目标签和评分。它们来自 `episodes.json`。
- 不要说页面完全不允许滚动。桌面结果页以一屏为目标，移动端为了可用性保留正常滚动。
- 不要只讲视觉好看。重点要讲信息判断、证据边界、状态稳定和响应式取舍。
