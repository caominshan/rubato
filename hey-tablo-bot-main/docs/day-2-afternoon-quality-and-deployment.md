## 2. 为什么不能只做功能

面试中的 AI 项目经常出现三个问题：

- 只能现场点几下，无法证明结果不是写死的。
- README 只写启动命令，别人看不懂产品价值和技术决策。
- 声称“已经可上线”，但没有测试、错误降级和部署检查。

因此，本阶段不是继续堆功能，而是补齐三个证据层：

```text
自动化测试：证明核心行为稳定
工程文档：证明方案可以被他人理解
质量与评测：证明我知道系统能做什么、不能做什么
```

面试时可以这样概括：

> 我没有把“页面能跑”当作项目完成，而是继续补齐测试、持续集成、错误降级、移动端验收和评测报告，让项目的关键承诺都有证据。

## 3. 12 个测试具体验证了什么

测试分为两层：确定性检索层和 API/Agent 层。

### 3.1 检索与工具测试：7 个

#### 测试 1：字幕 Schema 完整性

验证 500 条字幕都符合统一的数据结构，包括 episode、时间戳、原文、中文含义、来源状态等字段。

它解决的问题是：数据字段缺失时，不应该等到页面渲染才报错。

#### 测试 2：精确英文短语检索

输入 `mentally bulletproof`，验证第一条结果来自预期集数，并且原文确实包含这句话。

它证明 MiniSearch 不只是模糊推荐，也能完成精确字幕检索。

#### 测试 3：中文需求检索英文字幕

输入“失恋后很难过，想被陪伴”，验证查询扩展能够命中相关英文字幕。

这对应产品的核心使用场景：用户用中文表达状态，但内容源主要是英文。

#### 测试 4：来源验证过滤

开启 `verifiedOnly` 后，所有结果的 `sourceVerified` 必须为 true。

这证明来源可信度不是界面标签，而是可以进入检索条件的业务规则。

#### 测试 5：节目与上下文工具

验证系统能返回单集元数据，也能以目标字幕为中心取得前后相邻片段。

这为后续“不要断章取义”提供数据基础。

#### 测试 6：推荐多样性

要求三条结果来自三个不同 episode。

如果三条都来自同一集，即使相关，也会让用户觉得系统只找到了一份内容。

#### 测试 7：重新规划强制去重

把第一轮 segmentId 放入 `excludeSegmentIds`，验证第二轮结果完全不包含它们。

这证明“不重复推荐”发生在检索代码中，而不只是提示模型“尽量不要重复”。

### 3.2 API 与 Agent 测试：5 个

#### 测试 8：非法请求

空字符串等非法输入会在运行 Agent 前返回 400。

这样可以避免为无效输入消耗模型调用费用。

#### 测试 9：模型不可用时降级

没有模型密钥时，系统仍然使用本地 MiniSearch 返回结果，并明确标记：

```text
mode = fallback
confidence = low
error.code = missing_api_key
```

它证明模型服务不是整个产品的单点故障。

#### 测试 10：Qwen 配置提示

当模型提供方设为 Qwen 但没有密钥时，错误信息必须提示 `DASHSCOPE_API_KEY`，而不是错误地提示 OpenAI 配置。

#### 测试 11：信息不足先澄清

输入“随便”时：

- 返回澄清问题。
- recommendations 为空。
- 工具调用数为 0。

它验证 Agent 知道什么时候不应该猜。

#### 测试 12：反馈驱动重新规划

点击“太说教”后，验证：

- `conversationId` 保持不变。
- `turn` 从 1 变成 2。
- `avoidAdvice` 更新为 true。
- 反馈被加入历史。
- 第二轮 segmentId 与第一轮没有交集。

这是对产品验收标准的完整自动化验证，而不只是检查页面有没有按钮。

## 4. GitHub Actions 做了什么

新增文件：`.github/workflows/ci.yml`。

它会在下面三种情况下运行：

- 向 `main` 分支推送代码。
- 创建或更新 Pull Request。
- 在 GitHub 页面手动触发。

执行顺序：

```text
Checkout 仓库
→ 安装 Node.js 22
→ npm ci 按 lockfile 安装依赖
→ TypeScript 检查
→ 运行 12 个测试
→ Next.js 生产构建
```

为什么使用 `npm ci` 而不是 `npm install`：

- `npm ci` 严格使用 `package-lock.json`。
- CI 和本地使用同一套依赖版本。
- lockfile 与 package.json 不一致时直接失败。
- 更适合可重复构建。

还增加了两个工程保护：

```yaml
timeout-minutes: 10
```

避免任务异常挂起。

```yaml
concurrency:
  cancel-in-progress: true
```

同一个分支快速推送多次时，取消过时任务，减少等待与资源浪费。

需要准确说明的是：当前项目目录还没有 `.git` 元数据，所以 workflow 文件已经写好，但要初始化仓库并推送到 GitHub 后才会真实运行。

面试时可以说：

> 我把 typecheck、12 个测试和 production build 设置为合并前的质量门禁。代码不是“在我电脑上能跑”就算通过，而是每次提交都必须在干净的 Node.js 22 环境中重新验证。

## 5. 移动端检查做了什么

项目使用 `720px` 作为主要响应式断点。本轮针对 360、390、430 像素常见手机宽度整理了移动端验收矩阵。

检查的不是单纯“页面有没有缩小”，而是以下场景：

| 场景 | 重点 |
|---|---|
| 初始首页 | 标题、插画、快捷需求和输入框不产生横向溢出 |
| 文本输入 | 输入字号可读、计数器可见、提交行为正常 |
| 推荐结果 | 声纹节点可点击、封面保持 16:9、标题不撑破容器 |
| 信息密度 | 摘要和理由限制行数，优先显示关键内容 |
| 四种反馈 | 小屏自动换行，按钮文字不被截断 |
| 加载状态 | 保留旧结果，不出现整页闪烁 |
| 错误状态 | 错误不会清空输入或遮挡主要操作 |
| 可访问性 | label、alt、aria-live 和 alert 仍然有效 |

移动端没有照搬桌面布局，而是进行了内容优先级调整：

- 页面切换为自然文档流，避免强行压缩成桌面单屏。
- 逐集封面保持 16:9。
- 详情从桌面分栏调整成适合窄屏的组合布局。
- 摘要和推荐理由限制行数。
- 次要编辑文案在窄屏隐藏。
- 保留标题、字幕原文、推荐理由、评分和反馈入口。

本轮没有引入 Playwright，因此移动端属于响应式代码检查与场景验收，不应该说已经完成自动化真机测试。

## 6. 错误状态如何分层

错误状态不是统一显示“请求失败”，而是根据问题发生的位置处理。

### 6.1 非法输入

例如少于 2 个字符、超过 300 个字符或 session 结构不合法：

```text
HTTP 400
code = invalid_request
```

### 6.2 JSON 格式错误

请求体无法解析时：

```text
HTTP 400
code = invalid_json
```

### 6.3 服务端异常

原来的 API Route 用一个大 `try/catch` 包住全部逻辑，这会导致 Agent 执行异常也被错误地返回成 `invalid_json`。

我将处理拆成三个阶段：

```text
解析 JSON
→ Zod 校验
→ 执行 Agent
```

真正的未知服务端异常现在返回：

```text
HTTP 500
code = internal_error
```

这使日志、前端提示和后续监控能够区分“用户请求有问题”与“服务器有问题”。

### 6.4 模型或工具失败

如果模型密钥缺失、模型请求失败或 Retrieval Agent 没有成功调用工具：

```text
真实 Agent 失败
→ 本地 MiniSearch 降级
→ 返回可用候选
→ 标记 fallback 和低置信度
→ Trace 保留失败原因
```

### 6.5 反馈重新规划失败

前端不会清空上一轮推荐，而是：

- 保留旧结果。
- 恢复按钮可点击状态。
- 在反馈区显示局部错误。
- 允许用户再次操作。

### 6.6 封面加载失败

YouTube 封面无法加载时切换到本地默认播客封面，避免图片裂开破坏整个结果卡。

面试时可以总结：

> 我按可恢复性设计错误状态。模型失败不等于产品完全失败，重新规划失败也不应该让用户丢掉上一轮可用结果。

- Schema 完整性。

- 来源过滤。
- 结果多样性。
- 多轮去重。

- 信息不足处理。
- 工程构建质量。

报告最后还明确下一阶段真正应该增加的指标：

- 20–50 条人工标注查询集。

## 14. 面试官可能追问的问题

### Q1：为什么只有 12 个测试？

两天 MVP 中优先覆盖最关键、最容易出错的业务承诺：数据合法、能找到证据、来源可过滤、反馈后不重复、模型失败可降级。后续再扩展 UI 端到端和真实模型集成测试。

### Q2：这些测试有没有真实调用 Qwen？

没有。自动化测试主要验证确定性逻辑和无密钥降级，避免 CI 依赖外部额度、网络和模型波动。真实模型工具调用属于单独的集成验收。

### Q3：为什么不在 CI 里直接调用模型？

真实模型测试成本高、结果有波动，还涉及密钥管理。CI 先保证确定性业务逻辑；线上或定时评测可以另外运行少量带密钥的集成用例。

### Q4：为什么还需要 production build？

测试通过不代表 Next.js 能生产构建。build 可以发现服务端与客户端边界、类型生成、路由和打包阶段的问题。

### Q5：GitHub Actions 已经运行了吗？

配置已经完成，但当前目录还没有 Git 元数据，需要推送 GitHub 后才会运行。不能把“写好 workflow”说成“线上 CI 已成功”。

### Q6：移动端是怎么测的？

### Q7：为什么模型失败后还返回结果？

因为核心字幕检索是本地确定性能力。模型失败时仍可以提供候选，但必须明确标记 fallback、低置信度和来源状态，不能伪装成 Agent 正常完成。

### Q8：为什么不直接写推荐准确率？

因为没有人工标注查询集就无法严谨计算准确率。当前只报告可复现的测试通过率、Schema 完整性和来源覆盖率。

### Q9：README 对产品经理有什么价值？

它不仅是开发说明，也定义了产品定位、核心承诺、数据边界、异常策略和上线条件，是跨角色沟通材料。

### Q10：你认为本阶段最重要的产品判断是什么？

AI 产品不能只设计成功路径。用户输入不足、模型失败、反馈失败和来源未验证都是正常状态，必须在产品方案里有明确处理。
